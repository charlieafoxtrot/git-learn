This creates the local working folder C:\git\git-learn. Run the later Git commands from that folder, not from ProviderDev.

What origin means

When Git clones this repository, it names that GitHub remote origin. It is a local nickname Git assigned to the source repository, not a special server or a second copy of your files. For example, origin/main is your local record of the remote main branch.

Public clone does not automatically mean push access

Anyone can clone this public repository and read it. If you do not have permission to push to it, use GitHub’s Fork control first, then clone your fork before attempting to push. In that case, origin points to your fork.

The big picture

Two things working together

Git records the history of files in a local repository on your computer. GitHub hosts a shared copy of that repository and adds collaboration features such as pull requests, reviews, and automated checks.

A branch gives one focused change its own path through the local history. A pull request is the conversation and proposed merge on GitHub—not a Git command called “pull.”

Why is a pull request different from git pull?

git pull runs on your computer: it downloads changes from a remote repository and integrates them into your currently checked-out local branch. A pull request is a GitHub collaboration page: it proposes merging one branch into another, shows the diff, and collects review and check results. You can open a pull request without running git pull, and you can run git pull without opening one.

Keep this question handy

Where is my change right now: my working folder, my local Git history, or GitHub? The answer tells you the next useful action.

Main route

The everyday path

Think of a change as moving through places. You edit and record it locally, publish the branch to GitHub, then use a pull request to discuss and integrate it. This is the usual GitHub flow; repository rules may add steps.

Text route: edit in the working folder → commit to a local topic branch → push that branch to GitHub → open a pull request → reviewers and checks respond → merge the pull request into main → update local main. A reviewer does not receive your unpushed local commits.

GitHub Desktop and the command line show the same local story

In GitHub Desktop, select main, fetch/pull updates, create a branch, inspect changes, commit, and publish. The PowerShell sequence below names the same Git actions. Desktop can open or create a PR; use GitHub.com for the full review conversation, inline comments, and merge.

One ordinary, inspect-first PowerShell sequence

Run these commands in the root folder of your local clone. Branch and file names below are examples; use only a branch you intend to change. First make sure git status shows no work you need to keep before switching branches.

  1. Inspect before changing anything

    Runs locally in PowerShell, inside the cloned repository.

    git status

    Shows the current branch plus staged, unstaged, and untracked files. It does not change files or history.

  2. Move to and update local main

    Runs locally; switch only after you have dealt with work shown by git status.

    git switch main
    git pull --ff-only origin main

    git switch main checks out your local main. The pull downloads origin/main and integrates it only if a fast-forward is possible; it stops rather than making an unexpected merge commit.

  3. Create one focused branch

    Runs locally; this branch name is an example.

    git switch -c docs/add-remediation-guidance

    Creates and checks out a local topic branch starting from the updated main.

  4. Edit, then inspect the change

    Edit in your local folder; inspect in PowerShell.

    git status
    git diff

    git diff shows unstaged edits compared with the current commit. Read the diff before deciding what belongs in this commit.

  5. Stage exactly what you intend, then re-check

    Runs locally; replace the path with a changed file.

    git add -- path\to\changed-file.md
    git diff --staged

    Staging chooses the snapshot for the next commit. The staged diff is your last local review before recording it.

  6. Commit and publish the topic branch

    Runs locally; publishing sends commits to the named remote when you have access.

    git commit -m "docs: add remediation guidance"
    git push -u origin docs/add-remediation-guidance

    The commit records the staged snapshot in your local history. Push publishes those commits to a remote branch; -u remembers that upstream for later pushes and pulls.

After the push, use GitHub.com to open a pull request from the topic branch into main, inspect its diff, and follow the repository’s review and checks requirements. See GitHub’s pull-request overview for the collaboration model.

Vocabulary

What the words mean

Working directory

The files you can edit right now in your local folder.

Staging area

The selected snapshot for the next commit. git add puts changes here.

Commit

A named snapshot recorded in local Git history, with a message and parent history.

Local branch

A movable label in your local Git repository, such as main or a topic branch.

Remote-tracking branch

Your local record of a remote branch, such as origin/main. git fetch updates it; it is not a separate checkout.

Push

Publish local commits to a branch on a remote such as GitHub. It does not create a pull request by itself.

Pull request

A GitHub collaboration object that proposes merging a head branch into a base branch. It is not the git pull command.

Review and checks

People comment or approve; automated checks report whether configured work passed. Both appear around the pull request.

Merge

Integrate the proposed branch’s changes into the target branch, commonly main, using the method allowed by that repository.

git fetch

Downloads remote updates and updates remote-tracking branches such as origin/main. It does not integrate those updates into your checked-out branch. Read the official Git documentation.

git pull

Fetches, then integrates the configured remote branch into the branch currently checked out. With explicit arguments, git pull origin main names the source. Read the official Git documentation.

git push

Publishes your local commits to a remote branch. After pushing a topic branch, GitHub can offer a pull request, but the pull request remains a separate GitHub step.

One word, two different ideas

Pull request means “please merge this GitHub branch into that one.” git pull is a local Git command that fetches and integrates history. The similar names do not make them the same operation.

Make a choice

Branch, fork, clone, or worktree?

These words describe different things. A clone is a local repository copy; a branch is a line of history inside a repository; a fork is a separate GitHub-hosted copy; a worktree is another local folder attached to one clone.

Choose the smallest thing that solves your situation
If you want to…Use…Why
Work on one change without affecting mainA branchA separate line of commits inside the same repository.
Get a full local copy of a GitHub projectA cloneFiles and history live on your computer and can sync with a remote.
Propose changes when you cannot push to the original projectA forkYour own hosted copy can receive your branch and send a pull request upstream.
Keep two branches checked out in folders at the same timeA worktreeAdditional working folders share one local repository's object history.

Example: add a second worktree

Run from C:\git\git-learn; choose a folder name that does not already exist.

git worktree add -b practice/side-task ..\git-learn-side-task main
git worktree list

This creates a new branch from main and checks it out in C:\git\git-learn-side-task. Your original folder stays on its current branch.

Before removing a worktree

Check for uncommitted changes and preserve anything you need. Remove a clean linked worktree from another worktree with git worktree remove ..\git-learn-side-task. Removing its folder does not automatically delete its branch. GitHub Desktop also documents worktree management; the CLI exposes the same Git worktree feature through explicit commands.

Collaboration

Pull requests and review

A pull request (PR) proposes changes from a head branch into a base branch. In the first `git-learn` exercise, the head is `practice/edit-story` and the base is `main`.

What reviewers do

  • Comment: ask a question or suggest an improvement.
  • Request changes: identify work needed before approval.
  • Approve: say the change is ready under that reviewer's judgment.

For a small practice PR, read the conversation and Files changed view. You can inspect your own PR, but GitHub does not let you approve your own pull request.

How the branch gets updated

Address feedback on the same topic branch. Each new commit you push updates the open PR automatically. Reviewers can then inspect the new diff and refresh their decision.

The PR page gathers its description, comments, commits, file diff, checks, and merge readiness in one place.

Common ways GitHub can integrate the pull request
Merge methodWhat happens to historyBeginner picture
Merge commitCombines the topic branch history into the base and records a merge commit.Keep the branch commits and show where the paths joined.
Squash and mergeCombines the topic branch changes into one new commit on the base.Many small practice commits become one tidy commit.
Rebase and mergePlaces the topic commits after the base's latest commit, creating a linear history.Keep the commits in a straight line.

Repository rules decide what is allowed

Projects can require approvals and checks, restrict who merges, or allow only some merge methods. Follow the status and guidance shown on that repository's PR; do not assume every project uses the same rules.

See GitHub Docs on pull requests and writing code for a project.

Automation

GitHub Actions in context

GitHub Actions runs automated work from a workflow file in the repository. A workflow can start when someone pushes a branch, opens or updates a pull request, or manually starts it.

Remember

  • Not every repository has automated workflows.
  • Checks run from project-defined workflow files and may need setup or secrets.
  • A failed check links to logs that help identify the step that failed.
  • Only checks marked as required by repository rules block merging.

Practice repo status

The git-learn lessons explain the idea without asking you to configure automation. No existing Actions setup is being claimed for ProviderDev. A future hypothetical project might check formatting or validate a Terraform plan on a pull request.

Recover calmly

Common snags

When something looks wrong, pause and inspect before changing history. Start with git status; it tells you the current branch and whether there are edits to protect.

Safe first moves for common situations
SituationInspectNext safe move
Your branch is behindgit statusKeep your work safe, switch to main, then use git pull --ff-only origin main. Return to your topic branch and follow project guidance to update it.
Review asks for a changeRead the comment and PR diffEdit on the same topic branch, inspect the diff, commit, and push. The PR updates automatically.
A merge conflict appearsgit status and the marked filesChoose the intended combined content, remove conflict markers, review the whole file, then stage and complete the merge. Ask for help if the intended result is unclear.
You may be on the wrong branchgit branch --show-current and git statusDo not switch blindly if there are edits. Preserve or commit the work first; then move to the right branch.
Push is rejectedgit status and the full errorFetch or pull the latest base as appropriate, resolve any conflict, then push again. Do not force-push a shared branch unless the project explicitly instructs you.

A safe pause

Avoid git reset --hard and force-push while learning; they can discard work or rewrite commits other people rely on. Ask someone to inspect with you before using them.

Words to remember

origin
The usual short name for the remote you cloned from (often your fork if you cloned your fork).
upstream
Often the original project remote when working from a fork; context matters.
fetch
Download remote history and branch updates without integrating them.
pull
Fetch updates and integrate them into the current branch.
base / head
The destination branch and the proposed source branch of a PR.
worktree
A linked working folder for another branch of the same local repository.
